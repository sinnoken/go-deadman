# 以精實管理規劃 agent 分工（通用方法）

本文件是通用方法，可套用到任何 repo：從**領域、程式碼、架構**三個角度，推導出需要哪些 agent、怎麼分工、怎麼交接。最後的附錄示範套用到本 repo 的結果。

## 1. 原則：每個 agent 都要有存在的理由

精實管理的核心是消除浪費。每多一個 agent，就多一次交接、多一次重讀上下文、多一個等待點。所以預設是**越少越好**，只有符合下列至少一項，才把一件工作獨立成 agent：

| 代號 | 獨立的理由 | 判斷方式 | 精實觀點 |
|---|---|---|---|
| R1 | 不同的專業知識 | 這件事需要的知識，主要工作者通常不具備 | 避免缺陷與重工 |
| R2 | 不同的權限範圍 | 能改的檔案或能用的工具明顯不同（例如只能讀、只能改資料） | 防呆：權限就是邊界 |
| R3 | 可以平行、互不等待 | 與其他工作沒有先後依賴 | 縮短交付時間 |
| R4 | 必須由他人驗證 | 作者不能審查自己的成果 | 自働化：發現缺陷就停線 |

四項都不符合時，併入相鄰的 agent。

## 2. 三個分析角度：從哪裡找出候選 agent

### 2.1 領域

找出需要專業判斷的知識區塊。

| 要問的問題 | 可能產生的角色 |
|---|---|
| 有沒有需要外部知識或實測才能維護的資料或內容？（設定清單、規則表、資料集、翻譯） | 資料策展者 |
| 有沒有法規、安全、合規要求？ | 安全審查者 |
| 不同平台（作業系統、瀏覽器、硬體）的行為有沒有差異？ | 平台驗證者 |
| 使用者是誰？需不需要使用體驗或文案的專業？ | 文件撰寫者、體驗設計者 |

### 2.2 程式碼

從 repo 的實體結構，判斷誰會改哪裡。

| 要看的東西 | 判斷方式 |
|---|---|
| 語言與技術棧 | 有兩種以上技術棧（例如 Go 後端加 TypeScript 前端），才考慮分開實作者；只有一種就用一個實作者 |
| 目錄的擁有權邊界 | 例如 `cmd/`、`internal/`、`web/`、`data/`、`docs/`。哪些目錄常一起改？哪些各自獨立？ |
| 測試結構 | 單元測試與整合測試若需要不同環境（網路、真實裝置），驗證工作可以獨立出來 |
| 自動產生的檔案 | 只由產生它的腳本或負責人更新，其他人不手動修改 |
| 變更熱區 | 用 `git log` 看修改頻率與「常一起修改」的檔案；常一起改的區域交給同一個 agent，避免交接 |

### 2.3 架構

從系統分層與交付流程，看價值怎麼流動。

| 架構元素 | 對應的職責 |
|---|---|
| 進入點與介面層（CLI、API、UI） | 實作者；介面層有專屬技術棧時才分出去 |
| 核心領域邏輯 | 實作者 |
| 對外整合層（網路、資料庫、第三方 API、作業系統呼叫） | 平台驗證者，僅在需要真實環境驗證時獨立 |
| 設定與資料 | 資料策展者 |
| 建置、CI、發布、部署 | 發布負責人 |
| 對外文件與規格 | 文件撰寫者 |

## 3. 通用角色目錄

| 角色 | 何時需要 | 符合的理由 | 權限 | 完成定義 |
|---|---|---|---|---|
| 協調者（主工作階段） | 一律需要 | 無；負責整體流動 | 全部 | 使用者確認 |
| 實作者 | 一律需要 | R2 | 只能改程式碼與測試 | 本機標準檢查全部通過 |
| 審查者 | 一律需要 | R4 | 唯讀 | 依嚴重度列出問題，不灌水 |
| 發布負責人 | 有發布流程時 | R2、R3 | git、CI、發布工具 | CI 全部通過，產物驗證無誤 |
| 文件撰寫者 | 文件會隨程式碼變動時 | R2、R3 | 只能改文件 | 文件內容與實際行為一致 |
| 資料策展者 | 領域中有需要外部驗證的資料時 | R1、R2、R3 | 只能改資料檔 | 每筆資料都有驗證依據與日期 |
| 平台驗證者 | 有平台差異、需要在真實環境驗證時 | R1 | 執行與實測 | 在目標環境實測通過 |
| 安全審查者 | 有安全或合規要求時 | R1、R4 | 唯讀 | 列出風險與處理方式 |
| 第二位實作者 | 有第二種技術棧時 | R1、R2 | 只能改該技術棧的程式碼 | 該技術棧的檢查全部通過 |

### 規模參考

| repo 規模 | 建議的 agent 數 |
|---|---|
| 小型：單一語言、單一維護者 | 協調者，加上 3～5 個 agent |
| 中型：多模組或多平台 | 5～7 個 agent |
| 大型：多技術棧、多團隊 | 依限界脈絡（bounded context）分組，每組 3～5 個，再加一位跨組的發布負責人 |

規模小時，「平台驗證」「安全審查」可以先併入實作者或審查者的完成定義，等工作量變大再獨立。

## 4. 流程規則（所有 repo 共用）

```
需求 → 協調者分類
        ├─ 程式碼變更 → 實作者 ─┐
        └─ 資料變更 → 資料策展者 ┤   彼此獨立，可平行進行
                                 ▼
                   本機標準檢查（一個指令跑完） ← 失敗就停線
                                 ▼
          審查者 ∥ 文件撰寫者 ∥ 平台驗證者   （平行進行）
                                 ▼
          修正 → 發布負責人 → CI → 發布 → 驗證產物
```

1. **拉式、小批量**：同時只進行一個發布；每次發布只處理一個主題，審查時才看得完。
2. **標準作業先於 agent**：重複的步驟一律做成 repo 內的腳本，agent 只負責呼叫，不自己組指令。常見的有：
   - 環境準備（安裝並鎖定工具版本）
   - 本機總檢查（格式、靜態分析、測試、安全掃描）
   - CI 監看
   - 資料驗證
3. **單一事實來源**：資料只存在一個地方，其他東西都從它推導出來，不要複製一份另外維護。
4. **停線（自働化）**：
   - 本機檢查失敗，就不推送。
   - CI 失敗，就不發布。
   - 審查有「必須修正」的項目，就不發布。
5. **權限就是邊界**：每個 agent 只能修改自己負責的路徑，審查者一律唯讀。
6. **先回答，再回報**：使用者提問時，協調者在回覆的第一段就直接回答，進度回報放在後面。

## 5. agent 定義範本

放在 `.claude/agents/<name>.md`：

```markdown
---
name: <角色名稱>
description: <何時該派這個 agent，寫成觸發條件，例如「修改 presets/ 底下的資料時」>
tools: <最小必要工具，例如 Read, Grep, Bash>
model: <機械性工作用較小的模型，需要判斷的工作用較大的模型>
---
## 範圍
- 可修改：<路徑>
- 不可修改：<路徑>

## 標準作業
- 開始前執行：<腳本>
- 完成前執行：<腳本>

## 完成定義
- <可以驗證的條件>

## 回報格式
- 改了哪些檔案
- 驗證結果
- 待決事項
```

## 6. 改善指標

| 指標 | 反映什麼 |
|---|---|
| 交付時間（從需求到發布） | 流動效率 |
| CI 一次通過率 | 標準作業是否有效 |
| 每次發布後的修補提交數 | 重工程度 |
| 每個需求經過的 agent 數 | 分工是否過細 |
| 使用者重複詢問的次數 | 溝通是否有效 |

出現下列情況時，重新檢討分工：

- 新增技術棧或發布平台。
- 開始有外部貢獻者。
- 某個 agent 的重工率持續偏高。
- 某個 agent 長期閒置。這時應該把它併入其他角色。

## 附錄：套用到本 repo（go-deadman）

| 分析角度 | 觀察 | 結果 |
|---|---|---|
| 領域 | 網路延遲量測；`presets/` 的目標必須從使用者的網路實際 ping 過才能加入 | 資料策展者（R1、R2、R3） |
| 領域 | Windows 與其他系統的 ICMP、計時行為不同 | 平台驗證：規模小，先併入實作者的完成定義（在 Windows 上實際執行） |
| 程式碼 | 只有 Go 一種語言；`cmd/` 與 `internal/` 常一起修改 | 一位實作者 |
| 程式碼 | `presets/*.yaml` 與程式碼各自獨立變動 | 資料策展者與實作者可以平行進行 |
| 架構 | 有 CI、以 tag 觸發發布、會產生 Release 產物 | 發布負責人 |
| 架構 | README、CLAUDE.md、`.github/copilot-instructions.md` 會隨行為改變 | 文件撰寫者 |
| 通則 | 作者不能審查自己的成果 | 審查者（唯讀） |

結果：協調者加上 5 個 agent（實作者、資料策展者、審查者、文件撰寫者、發布負責人），屬於小型 repo 的配置。
